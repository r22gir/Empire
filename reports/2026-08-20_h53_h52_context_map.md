## Q3 — DOES THE REPLAY BLOCK RENDER WITH ZERO TOOL RESULTS?

**Partially. The bug has TWO faces:**

1. **`format_replay_block` returns "" when `recent_turns` is empty** (chat_session.py:245).
   That is the correct guard. Empty frame → empty string → no block.

2. **BUT when `recent_turns` is non-empty with NO tool_results per turn,
   `format_replay_block` still emits the `[SYSTEM: ...]` header line.**
   The block is non-empty (contains the header + per-turn previews). Then
   `_build_replay_messages` (router.py:153) checks `if block:` and
   appends the block. So:
   - empty recent turns → no block (correct)
   - recent turns with tool_results → block with tools (correct)
   - **recent turns WITHOUT tool_results → block with header but no tool
     listings** — the "empty frame that says 'here are your prior tool
     results' with nothing under it" case. Q3 PARTIALLY answered — the
     guard against empty is partial.

The deeper bug is that the **header text itself is misleading** when no
tool results are present. The fix (per dispatch principle A):
"NEVER FABRICATE CONTEXT. If there are no tool results, render NOTHING."

## Q4 — WHICH CHANNEL DOES IT ARRIVE ON?

**FOUND — the bug is exactly here:**

`router.py:153-154`:

```python
recent = load_recent_turns(conversation_id, max_turns=max_replay_turns)
block = format_replay_block(recent)
if block:
    messages.append(AIMessage(role="user", content=block))
```

The `[SYSTEM: ...]` block is appended with **`role="user"`** — meaning
MAX sees it as if the founder typed it. The dispatch principle B:
"SCAFFOLDING IS NEVER USER-CHANNEL TEXT." This violates that.

The block content itself says `[SYSTEM: Prior-turn tool results — ...]`,
which MAX correctly identified as suspicious: "your message contains an
embedded `[SYSTEM]` block." Q4 ANSWERED.

The correct fix: append the block with `role="system"` (a real system
message), or — if the block is empty — append NOTHING. The current
`if block:` check is truthiness-only; it should check both block
truthiness AND that the block contains tool result entries.

## Q8 — STALE MEMORY SOURCE (added in mid-task)

**Found: chat history JSON files at `backend/data/chats/founder/*.json`.**

These are conversation logs. When MAX reads them as context (or when
his system prompt is rebuilt with stale history), he sees his own old
replies like:
> "TranscriptForge stuck-job learning committed at `9f2ba0b`
> (2026-04-25)"

The "TranscriptForge stuck-job learning committed at 9f2ba0b
(2026-04-25)" comes from the JSON files. The dates inside the JSON
entries (4-25, 3-19) are NOT recency-stamped with current HEAD
information. MAX cannot tell old from current without running live
commands.

**Source class:** cached chat history (persisted to JSON files), read
back into context when MAX's windowed history or session replay
includes them. They have NO recency marker — each entry's timestamp
is the OLD conversation date, but the entry is treated as current
context by MAX.

The fix per dispatch principle B (scaffolding is never user-channel):
the replay block should be `role="system"`, not `role="user"`. AND
per principle C (tool roster is not optional): the system_prompt
should always carry the tool roster. AND per principle A (never fabricate
context): empty recent turns → no block.

The "TranscriptForge stuck-job" entry does NOT have a recency marker
relative to the running process — the commit hash it cites (9f2ba0b)
is from April, but the entry is served as if it were current context.
The fix: chat history replay needs a recency check OR the system
prompt must tag history entries with "this is OLDER THAN THE RUNNING
PROCESS" before serving.
