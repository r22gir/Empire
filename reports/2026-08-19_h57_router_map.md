## §2 WHAT is the trigger?

**Keyword substring match.** Literal tuple at
**`drawing_intent.py:24-43`**. First 3 keywords (verbatim):
```python
DRAWING_KEYWORDS = (
    "drawing",
    "render",
    "sketch",
    ...
)
```

The check is `is_drawing_intent(text)` at **`drawing_intent.py:335`**:
```python
return any(keyword in lowered for keyword in DRAWING_KEYWORDS)
```

The substring `"drawing"` is in `DRAWING_KEYWORDS` — **any** message
containing the literal substring "drawing" triggers the router.
"what is a drawing" contains "drawing". The long dispatch paste contains
"drawing". Bare "what?" / "what/" does not contain any keyword.

Negative patterns (per `drawing_intent.py:339-376`) do NOT include
question forms (`"what is"`, `"explain"`, etc.) — only explicit user
rejections ("don't draw", "no drawing-router", etc.). So a question
about drawing routes through.

## §3 IS IT PRE- OR POST-MODEL?

**Pre-model.** Evidence:
- `router.py:2367` calls `build_drawing_handoff` BEFORE any MAX
  invocation. The handoff result is rendered by `_drawing_render`,
  the response is formatted into a `ChatResponse` with `model_used =
  "drawing-router"`, and `return ChatResponse(...)` exits the chat
  handler. MAX is NEVER called.
- Same flow at `router.py:3145-3189` for the stream handler.
- The chat-handler's MAX invocation (`_invoke_max_agent` or equivalent)
  does not happen if the drawing route fires.

Confirmation: the founder's pasted dispatch paste (probe B) never
reached MAX — the router consumed the turn before MAX was invoked.
That's the pre-model pattern.

## §4 WHAT STATE does the router hold across turns?

`pending_drawing_jobs` table — SQLite-backed snapshot of partial
handoffs. Module at
**`/home/rg/empire-repo-main/backend/app/services/max/drawing_pending.py`**.

Lifecycle:
1. `build_drawing_handoff` returns a handoff with `missing_template_keys`
   (e.g. `["width", "drop"]`) when the founder's message references
   drawing intent but supplies no dimensions.
2. `router.py:2393-2401` saves the snapshot via `set_pending(...)`.
3. NEXT turn: `router.py:2361-2374` reads `pending = get_pending(...)`.
4. `is_continuation_reply(msg_text, pending["missing"])` checks whether
   the next message plausibly answers the pending question
   (`drawing_pending.py:123-140` — contains a dim-keyword OR mentions
   one of the missing keys explicitly).
5. If the next turn IS a continuation: merge and resume.
6. **If NOT a continuation: `pending` is KEPT.** The router fires
   again on the next turn, sees the same pending, asks for the same
   keys. This is the lag source — a half-formed drawing spec keeps
   soliciting every turn until the founder explicitly answers.
7. `clear_pending` is called only on cancel keywords ("never mind",
   "drop it", "cancel") or after a successful render.

`clear_handoff_state()` (`drawing_intent.py:49-60`) clears the
in-process `_LAST_HANDOFF` global at the start of every chat turn
(line 2346-2350 in router.py), but does NOT touch the SQLite
pending table.

## §8 KEY FINDINGS for Phase 2

1. **Trigger is keyword substring.** `"drawing"` alone is the first
   keyword — fires on any mention, in any context. Fix: route on
   INTENT TO GENERATE, not on vocabulary. A question about drawing
   is not a generation request.
2. **Pre-model interception.** Fix: when uncertain, the message goes
   to MAX. The router must never be the last word on an ambiguous turn.
3. **Pending table can leak.** A half-formed spec persists across turns
   until explicitly answered or cancelled. Fix: any non-answer to
   the solicitation releases the turn back to MAX (and the pending is
   abandoned, not carried forward).
4. **Two keyword lists** (MAX in `drawing_intent.py` vs HERMES in
   `openclaw_worker.py:1277`). Fix (later): consolidate.
