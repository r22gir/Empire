## 3 · IS GROUND TRUTH ALREADY AVAILABLE? (DISPATCH §3)

### 3.1 The runner's view at validation time

The `CodeTask` dataclass (`code_task_runner.py:631-705`) carries:

- `created_at: str` — ISO timestamp set at `submit()` (line 650, 720-721).
- `started_at: str` — ISO timestamp set at top of `_execute()` (line 651, 739).
- `completed_at: str` — ISO timestamp set at the end of each terminal path (line 652; e.g. line 965, 980, 1008, 1026, 1038, 1045, 1055, 1064).
- `executed_tool_calls: list[dict]` — full record per call, including `tool`, `params`, `success`, and `result` (line 657, 879, 949).
- `verified_commit_hash: Optional[str]` — set by `_repo_head_commit()` after a `git_ops commit` (line 659, 909).
- `log: list[CodeTaskLog]` — append-only event log with timestamps (line 661, 668-673).
- `files_changed: list[str]` — the validator's *output*, NOT ground truth (line 655, 950).

The runner does **NOT** carry:

- A `repo_path` field. The only repo path reference is hardcoded inside `_repo_head_commit()` at `code_task_runner.py:459` as `cwd=os.path.expanduser("~/empire-repo")` (STALE per dispatch).
- A working-directory or working-set field.
- A snapshot of `git status --porcelain` at task start.
- A mtime baseline for any file.
- A pre-task list of expected changed paths.

So the runner currently knows the start time and the full tool-call history;
it does **not** know what the repo looked like at start.

### 3.2 What exists elsewhere in the codebase (relevant, but on a different path)

`backend/app/services/openclaw_worker.py` — the *other* code-task path —
already implements a ground-truth capture:

- `_git_head()` at `openclaw_worker.py:314-327` — runs `git rev-parse HEAD` (cwd=REPO_DIR).
- `_git_changed_files()` at `openclaw_worker.py:346-369` — runs `git status --porcelain`.
- `_git_files_changed_between(before, after)` at `openclaw_worker.py:372-385` — runs `git diff --name-only before..after`.

The wrapper uses these at `openclaw_worker.py:1028-1038`:

```python
before_files = _git_changed_files()
before_head = _git_head()
execution = await _execute_task(task)
after_files = _git_changed_files()
after_head = _git_head()
commit_hash = after_head if before_head and after_head and after_head != before_head else execution.commit_hash
files_modified = (
    _git_files_changed_between(before_head, after_head)
    if before_head and after_head and after_head != before_head
    else sorted(after_files - before_files)
)
```

**This is exactly the ground-truth mechanism the dispatch §3 asks about —
and it already exists in the codebase. The problem is it lives in
`openclaw_worker.py` and only runs on the openclaw bridge path.**

It does **not** run when a task is submitted via `/api/v1/max/code-task`
(see §5 below). The code_task_runner has no equivalent.

### 3.3 What material exists to build a fix from (no design yet)

Available now, no design change required to access:

- `task.started_at` and `task.completed_at` — exact ISO timestamps bracketing the work.
- `task.executed_tool_calls[i].tool` — name of every tool that ran.
- `task.executed_tool_calls[i].params` — arguments. For `file_*`, this includes `path`. For `shell_execute`, this includes `command` (a free-form string). For `project_scaffold`, the `result` dict has `files_created: list[str]`. For `package_manager`, the `result` dict has `output` text only (no path list).
- `subprocess.run` access to `git` from the backend process — already used at `code_task_runner.py:458`.
- `os.getcwd()` — the backend process's cwd (which is `~/empire-repo-main/backend` because that's where uvicorn was started; per the dispatch's path doctrine the canonical repo is `~/empire-repo-main`).
- The `_git_changed_files()` and `_git_files_changed_between()` helpers in `openclaw_worker.py` — already importable, but bound to the openclaw_worker module's `REPO_DIR = "~/empire-repo"` (line 1174) which is STALE per dispatch.

Missing (would need to be added):

- A canonical repo path resolution (one source of truth, not the hardcoded `~/empire-repo` in `_repo_head_commit()` or `REPO_DIR` in `openclaw_worker.py`).
- A `task_start_files_snapshot` field on `CodeTask` to hold the pre-task `git status --porcelain` for the diff.
- The runner's own copy of the openclaw_worker ground-truth pattern (currently a single shared module would be the cleanest extraction, but that is a design choice — out of scope for this map).

The smallest correct fix uses material that is already available: capture
`git status --porcelain` (or `git rev-parse HEAD`) at `_execute()` entry,
capture it again at the end, and diff. The runner has all it needs to do
this; the only thing missing is the *call*.

### 5.2 What happens to in-memory state on restart

`code_task_runner` is a module-level singleton
(`code_task_runner = CodeTaskRunner()` at `code_task_runner.py:1073`).
`CodeTaskRunner.__init__` sets `self._tasks: dict[str, CodeTask] = {}`
(line 712). When the backend process exits or is restarted, the dict
is destroyed. **All `CodeTask` objects, all their `executed_tool_calls`,
all their `files_changed`, all their `error` strings, all their
`verified_commit_hash` values are gone.**

The R9 Phase 3 task (id `32c030a1-45a`) was submitted via Path B at
21:30 EDT, marked `error` because of the blind spot, and is now (after
the R9 restart at line ~38 of the Phase 3 report) **no longer
queryable** from `GET /api/v1/max/code-task/<id>/status` — `task =
code_task_runner.get_task(task_id)` returns `None` (line 5054) and the
endpoint raises 404. The evidence we have for that task is the live
R9 Phase 3 report file, the 30-byte scratch file on disk, and the
backend process's STDOUT — that's it.

### 5.3 Is any task submitted via Path B durably recorded ANYWHERE?

**No.** Searched the runner for any DB write:

in code_task_runner.py

Path B tasks live in `code_task_runner._tasks` and nowhere else. The

status payload is also lost on restart.

**This is a finding in its own right.** Phase 3 demonstrated that Path B
exists, that the live task was lost on the very next restart, and that
there is no DB record of it. Every Path B submission since the runner
was first wired up has been silently lost on every backend restart. If
the founder has been submitting code tasks through the portal Code Mode

### 12.2 Bisection

Ran the full suite minus subsets and binary-searched the polluter.
The polluter narrowed to `tests/test_founder_pin_failclosed_hotfix4_2.py`

### 12.3 Root cause

`test_founder_pin_failclosed_hotfix4_2.py` uses a fixture (`rel_module`,
`set_PIN`) and several test bodies to verify the FOUNDER_PIN
fail-closed behavior. To test the module-level env-var read, the
fixture does:

```python
for mod_name in list(sys.modules):
    if mod_name.startswith("app.services.max.tool_executor"):
        del sys.modules[mod_name]
return importlib.import_module("app.services.max.tool_executor")
```

After this test runs, `sys.modules['app.services.max.tool_executor']`
is a fresh module object. The reference bound at my R11 test's
import time:

```python

```

points to the **OLD** module (now unreferenced from sys.modules but
still alive in memory because I hold a reference). My
`monkeypatch.setattr(tool_executor_module, "execute_tool", mock)`
patches the OLD object. The runner does:

```python

```

inside `_execute()`. This looks up `app.services.max.tool_executor`
in `sys.modules` — which is the NEW module — and binds `execute_tool`
from the NEW module. My patch is invisible to the runner.

The same pattern is used in `test_code_task_runner_evidence.py`
(9 tests, pre-existing failures) but the existing failures there
are not caused by the patch (those tests fail because the runner's
mock expectations don't match the runner's actual behavior — the
patch is correctly applied). My R11 tests failed because the patch
was NOT being applied.

### 12.4 The fix

In `test_r11_validator_ground_truth.py`, all four `monkeypatch.setattr(...,
"execute_tool", mock)` call sites now resolve the module via
`sys.modules['app.services.max.tool_executor']` AT THE START of
each test, through a small helper `_live_tool_executor()`. The
runner re-imports from `sys.modules` for every `_execute()` call,
so we always patch the object the runner will see.

```python
_TOOL_EXECUTOR_NAME = "app.services.max.tool_executor"

def _live_tool_executor():
    """Return the CURRENT tool_executor module object from sys.modules.
    Required because test_founder_pin_failclosed_hotfix4_2.py reloads
    this module; any reference captured at import time is stale after
    that test runs."""
    return sys.modules[_TOOL_EXECUTOR_NAME]
```

Each call site: `monkeypatch.setattr(_live_tool_executor(),
"execute_tool", mock)` instead of `monkeypatch.setattr(tool_executor_module,
"execute_tool", mock)`.

### 13.1 What it would take to write API-path tasks to `openclaw_tasks`

**One commit, or its own round? — Its own round.** Here is the
scope of the work:

1. **No DB write in `code_task_runner` today.** The runner only
   mutates `self._tasks: dict[str, CodeTask]`. Adding an INSERT
   to `openclaw_tasks` would couple the runner to the openclaw
   schema.

2. **Schema alignment.** `openclaw_tasks` has the columns
   `title, description, desk, priority, source, status, result,
   error, files_modified, commit_hash, retry_count, max_retries,
   parent_task_id, started_at, completed_at, created_at` (init_db.py:308-328).
   A `CodeTask` carries `id, prompt, working_dir, execution_mode,
   provider_used, model_used, executed_tool_calls, files_changed,
   files_inspected, verified_test_runs, verified_commit_hash,
   verification_notes, log, last_response_text, last_function_calls_summary,
   last_parse_outcome`. They overlap on `id, result/error, files_modified,
   commit_hash, started_at, completed_at, created_at` (the
   `CodeTask.id` is a 12-char uuid prefix; `openclaw_tasks.id` is
   INTEGER AUTOINCREMENT — schema conflict).

3. **The cleanest path** is a thin writer module
   `code_task_persistence.py` that:
   - Subscribes to CodeTask state transitions (via callback or
     in-process queue).
   - Writes a row to `openclaw_tasks` on terminal state
     (COMPLETED, ERROR) with the schema-mapped columns.
   - On subprocess / API path. The openclaw bridge path already
     writes (it dispatches through `openclaw_worker._process_task`
     which UPDATEs `openclaw_tasks` directly).

4. **Risk:** the API path has no PIN-gated path in
   `submit_code_task` for non-founder channels. The persistence
   writer must NOT bypass PIN; founder channels pass via
   `is_founder_message()` already. Reuse the same gate.

5. **Migration of in-memory tasks at restart.** Out of scope for
   the persistence round; in-memory tasks created before the
   round are still lost. A future improvement could persist on
   submit (not just on terminal) so a backend crash mid-task
   doesn't lose the row.

6. **Estimated scope:** 1 file (`code_task_persistence.py`,
   ~80 lines), 1 test file (~5 tests), 1 small refactor to call
   the writer on terminal state, 1 commit. Plus 1 round of live
   proof (Phase-3 equivalent: submit a task via the API, verify
   the row exists in `openclaw_tasks` after a backend restart).

fix and the persistence fix are independent; bundling them

The model emitted `file_append` to `/tmp/r11_test_repo/...`; the path-safety check (`app.services.max.tool_safety.validate_path`, lines 44-87) refused the path: "escapes canonical root /home/rg/empire-repo-main." The model then fell back to writing at `/home/rg/empire-repo-main/r11_tracked_evidence.txt` (inside the canonical repo, which IS allowed). The validator, with `working_dir=/tmp/r11_test_repo`, saw 0 changes in the test repo and correctly marked the task as `error` (no file changes). The fix is correct; the test design is wrong.

The R11 fix's validator checks `git status --porcelain` in the `working_dir` the task was submitted with. If the file is written outside that working_dir, the validator correctly reports no changes. So for Phase 3:

- **`working_dir = /home/rg/empire-repo-main`** — the canonical repo. The model's natural fallback path (after path-safety refusal) is inside the canonical repo, which IS the working_dir. The validator's ground-truth capture sees the change.
- The on-disk evidence files are inside the canonical repo (untracked). They were cleaned up after Phase 3 completed (no repo pollution).

`/tmp` was NOT used for `file_append` because the pre-existing path-safety check refuses it (the exemption list at `tool_safety.py:26-29` is effectively unreachable for paths that fail the canonical resolver, which `/tmp` does — pre-existing design, not introduced by R11). `shell_execute` is exempt from `validate_path` (it goes through `validate_command` instead, which is permissive), so Task 2's `echo > /tmp/...` would have worked — but I kept both tasks on the same working_dir for consistency.
