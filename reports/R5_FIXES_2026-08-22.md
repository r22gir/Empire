**Question:** Is the fix one line or a migration?

**Answer:** **It is NOT a one-line fix in the sense the dispatch assumed** (point `/leads/` at `prospects`). Pointing `/leads/` at `prospects` would be wrong:
- Wrong lifecycle stage (scout pool, not active leads)

- No conversion record — `lf_prospects.converted_to_lead` and `lf_prospects.lead_id` would be bypassed
- The UI already shows the 322 prospects under the prospects tab via the correct route

**However, it is also NOT a database migration.** No data needs to be moved. The tables exist; the columns are correct; the conversion flow exists. The empty `lf_leads` is **truthful state** — no prospect has been promoted to lead yet.

**Question:** What is the actual fix?

**There is no bug in the router.** `/api/v1/leads/` correctly returns empty because `lf_leads` has 0 rows. The 322-row `prospects` table is correctly served by `/api/v1/leads/leadforge/prospects`, which the LeadForgePageNew UI already fetches.
