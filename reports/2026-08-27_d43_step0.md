## 0b · Source of the payload — UNIDENTIFIED

### Shape matched exactly

The 143 files in `backend/data/vision_inputs/` are byte-identical to the fixture defined in `backend/tests/test_vision_mmx_cli.py:12,17`:

```python
def _png_data_uri() -> str:
    payload = b"\x89PNG\r\n\x1a\n" + (b"x" * 128)
    return "data:image/png;base64," + base64.b64encode(payload).decode("ascii")
```

A similar but distinct shape (100 x's, not 128) exists in
`backend/tests/test_minimax_tools.py:73`. The 136-byte files do not match that
fixture (8 + 128 = 136, not 108).

The same magic (`\x89PNG\r\n\x1a\n`) appears in `test_archiveforge_workflow.py:17`,
but with a real (minimal) IHDR / IDAT / IEND payload, not 128 x's. So only
`tests/test_vision_mmx_cli.py:12,17` produces a byte-for-byte copy of what's on disk.

### Negative results

- **No cron, systemd timer, or apscheduler job** constructs the payload.
  `crontab -l` shows only a paused morning check, a disabled 0 3 old-lane
  backup, and the new canonical 0 3 backup (a683100). No `/api/v1/vision/*`
  traffic. systemd user timers list is empty for our units.
- **No background coroutine** in `backend/app/` calls `_materialize_image_input`
  or `_decode_image_input` outside HTTP requests. `main.py:419-456` starts
  `desk_scheduler`, `max_scheduler`, `max_monitor`, `vendorops_alert_runner`.
  None of those POST to `/api/v1/vision/*`.
- **No frontend placeholder.** The Next.js codebase
  (`empire-command-center/`) does not construct any PNG-magic + 128-x payload.
  The `iVBORw0KGgo` matches there are vendor three.js addons (`SMAAPass.js`,
  `SMAANode.js`, `Bayer.js` — SMAA shaders, not vision), and one
  `Reference/delivered/willard_3d/...html` — none of them POST to
  `/api/v1/vision/*`.
- **Smoke scripts checked:** `scripts/empire_smoke.py` is GET-only (no vision
  endpoint in `CHECKS`). `scripts/smoke_archiveforge.sh` uses a 1x1 real PNG
  (~67 bytes — `iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAQAAAC1HAwCAAAAC0lEQVR42mP8...`)
  which is not the 136-byte shape; nothing in that script touches
  `/api/v1/vision/*`.
- **RecoveryForge (3077) ruled out** by the dispatch audit.

### Access-log contradiction (suspicious)

systemd journal of `empire-backend` at the moment of writing
`vision-input-1787793253-e4f74b40.png` (2026-08-26 21:14:13 EDT, PID 1636966):

```
21:14:09 GET /api/v1/notifications
21:14:11 GET /api/v1/max/models
21:14:12 GET /api/v1/system/ollama/status
(no further log lines until 21:15:00 polling)
```

No POST to `/api/v1/vision/*` is logged for that minute or the surrounding
5-minute window. Yet the file is on disk, owned by PID 1636966 (the only writer
active — backend was restarted later at 21:54).

The `ls -la` of the directory confirms the PID at the moment of `write()`
(encoded in `int(time.time())` in the filename) lines up perfectly with the
journal entries for PID 1636966.

**Conclusion: the writer is unidentified.** The bytewise shape matches the
test fixture exactly, but the test fixture lives only in the test file. No
production code path, cron, or scheduler constructs this payload in a way that
goes through `uvicorn`'s access log.

This is, per the dispatch, an acceptable STEP 0 result and a finding in its
own right. **Until the writer is identified, the safest assumption is "test
fixture leakage into the live tree" by an as-yet-unknown mechanism** (cron, an
admin script run from the box, a developer-ad-hoc invocation that was never
cleaned up). After STEP 1's decode-verify guard, these posts will start
failing with 4xx, which will make the caller visible in the journal —
the dispatch explicitly notes this as the cheapest way to identify it.

## 0c · Downstream of a fake image — per endpoint

All seven POST endpoints traced. Pipeline:
`_materialize_image_input` (vision.py:185) → `_decode_image_input` (125) →
file written at vision.py:204 OR vision.py:214 → `call_minimax_image_understanding`
(472) → `minimax_understand_image` (minimax_tools.py:465) → `mmx vision describe`
subprocess → `_parsed_json_from_minimax_result` (vision.py:264).

**`xAI Grok fallback is disabled in production.** `MAX_DISABLE_XAI=true` is
set in the running service's environment (`/proc/<uvicorn-pid>/environ`), and
`VISION_ENABLE_XAI_FALLBACK` / `MAX_ENABLE_XAI_VISION_FALLBACK` are not set.
`_xai_vision_allowed()` returns False. Grok cannot silently fabricate numbers
from the 136-byte file. The downstream cascade below assumes only the
mmx-CLI primary path.

| Endpoint | Line | Body | Behavior on fake image |
|----------|------|------|------------------------|
| `POST /vision/measure` | 738-739 | `await call_vision(MEASURE_PROMPT, req.image)` (487) | Returns 200. mmx fails to decode → `result.success=False` → `_parsed_json_from_minimax_result` (line 280-285) → `_wrap_prose_as_empty_schema` (387) → F4 fallback dict with `width_inches: 0`, `height_inches: 0`, `confidence: 0`, `_vision_runtime.format_status="fallback_to_prose"`. |

### Class summary

- **All 6 in-scope POST endpoints return HTTP 200 with a degraded success-shaped
  body** when handed a 136-byte fixture. Never raises.
- The cascade is intentional: `_parsed_json_from_minimax_result` (vision.py:264)
  comments state the design — "Never raises — always returns a dict so
  /api/v1/vision/mockup is never a customer-facing 500".
- **Side effect on every fake call:** `_wrap_prose_as_empty_schema` calls
  `_notify_f4_fallback` (393 → 426) which writes a dashboard notification
  (always) and sends a Telegram ping (rate-limited to once per 10 minutes).
  Over 143 calls × N days this accumulates dashboard rows.

### What this means for past output

Per the dispatch: the user-facing harm is "silent-success". The bad files
themselves do not produce fabricated measurements — the F4 fallback zeros
them. But:
- Any MAX output in the 25 May – 26 Aug window that **claims** to describe an
  image is unfounded (per dispatch OPEN section).
- The 70-byte outlier (`vision-input-1780700316-a1301dc7.png`, dated 5 June)
  is not a real PNG either; same fate.
- The 4 × 1,541,248-byte files + 4 other real-looking files are real images
  (last real write 21 June per dispatch audit) and produce real vision
  output.

## Findings consolidated

1. **F-D43-1.** The decoder at `_decode_image_input` (vision.py:125-167)
   validates only:
   - base64 decodes cleanly (`b64decode(..., validate=True)`),
   - len(data) ≥ 32,
   - magic bytes resolve to a known image extension.

   That is **not image validation**. A 136-byte file containing only the PNG
   magic and 128 `x` characters passes all three checks. PIL would reject
   it: `verify()` raises `UnidentifiedImageError`.

2. **F-D43-2.** The writer of the 143 fake files is **unidentified** in
   STEP 0. The bytewise shape is byte-for-byte the fixture in
   `tests/test_vision_mmx_cli.py:12,17`. No production code, scheduled task,
   cron, MCP server, or front-end component constructs this payload.
   Critically, no POST to `/api/v1/vision/*` is logged at the moment a file
   is written. (See dispatch OPEN section: STEP 1 will turn the existing
   writes into 4xx, which will surface the caller in the journal.)

3. **F-D43-3.** The dispatch said `RecoveryForge` was ruled out; that
   finding is consistent with my own. No new writer found.

4. **F-D43-4.** All six in-scope POST endpoints return HTTP 200 with an
   F4-fallback success-shaped body when given the 136-byte fixture. **They
   do not raise.** This is the H76 class failure mode: silent success.
   Specifically:
   - `width_inches`, `height_inches`, `confidence` come back as `0`,
   - `proposals` come back empty,
   - `_vision_runtime.format_status = "fallback_to_prose"` is the only signal.

5. **F-D43-5.** xAI Grok vision fallback is **disabled** in the running
   backend (`MAX_DISABLE_XAI=true`, no `VISION_ENABLE_XAI_FALLBACK`). So the
   worst-case "model invents dimensions from a fake image" path is currently
   NOT reachable. `mmx` is the only path in production today.

6. **F-D43-6.** Each fake call writes a dashboard notification (always) and
   optionally a Telegram ping (10-min cooldown). 143 calls ⇒ 143 dashboard
   rows in 90 days. Worth knowing for cleanup.
