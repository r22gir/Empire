## The 1.2pt tolerance — my read

**The 1.2pt tolerance is too tight for a chrome that uses letterspacing on header/footer text.** The McLean reference's chrome spreads "POWERED BY EMPIRE WORKROOM" across the full page width. The descender of that letterspaced band brushes the next line's ascender, and the gate reports it as a collision.

**Three options, none of which I'm applying per directive:**

1. **Raise the tolerance to 4-6pt** (or 8pt). Filters out 12-13 of the 15 TOLERANCE entries. Loses the ability to catch real descender/ascender overlaps. The McLean reference was hand-tuned, so the actual overlaps at the 1.2pt threshold are a function of letterspacing, not a real defect.

2. **Per-class tolerance**: chrome header/footer = 8pt, body text = 1.2pt. Same effect but only on the strings that need it. Requires tagging each placed box with its class (header/footer/body) — a refactor.

3. **No tolerance, exact-overlap only**: raise to 0pt or check bbox intersection area > 0. The current 1.2pt is `ox > tol and oy > tol` (both axes). A pixel-perfect intersection catches only genuine overprints and skips the line-height brushing.

**My read: option 3 with a 0.5-1pt float for anti-aliasing safety.** Letterspaced text near a baseline is not a collision — it's a typographic property. The gate should report what would LOOK like overprint to a human reading the page, not what the BBox math says.

But this is a layering decision. The 9 REAL cases (items 1-8, 20) are about the **cover-index table** overflowing horizontally — not about line-height brushing. They need a layout fix in the cover builder, not a tolerance change. **The tolerance change filters TOLERANCE; it does not address REAL.** A separate fix for the cover-index overflow is needed.
