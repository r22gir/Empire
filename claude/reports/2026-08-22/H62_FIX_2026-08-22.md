#### Site 1 — `app/routers/max/router.py:5027` — `POST /code-task` (Code Mode)

```python
@router.post("/code-task")
async def submit_code_task(request: CodeTaskRequest):
    ...
    founder = is_founder_message(msg_ctx)
    if not founder:
        founder_pin = os.getenv("FOUNDER_PIN", "<PIN>")            # 5027 — BROKEN
```

- **What PIN is compared against:** `os.getenv("FOUNDER_PIN", "<PIN>")`.
  Match → proceeds to submit the code task as founder.
  Mismatch (or empty pin) → raises 403.
- **Caller gets on refusal:** **HTTP 403** with detail
  `"Invalid PIN. Code Mode requires founder authorization."`.
- **Behaviour change for legitimate callers after PART 2 fix:** NONE. The
  fix changes only the unset-env case (refuses instead of silently accepting
  the literal). A legitimate caller with the real PIN sees identical 200.

#### Site 2 — `app/routers/max/router.py:5060` — `POST /verify-pin` (PIN verify)

```python
@router.post("/verify-pin")
async def verify_pin(request: VerifyPinRequest):
    import os
    founder_pin = os.getenv("FOUNDER_PIN", "<PIN>")                # 5060 — BROKEN
    if str(request.pin) == founder_pin:
        return {"valid": True}
    raise HTTPException(status_code=403, detail="Invalid PIN")
```

- **What PIN is compared against:** `os.getenv("FOUNDER_PIN", "<PIN>")`.
  Match → returns `{"valid": True}`.
  Mismatch → raises 403.
- **Caller gets on refusal:** **HTTP 403** with detail `"Invalid PIN"`.
- **Behaviour change for legitimate callers after PART 2 fix:** NONE. Fix only
  affects unset-env case. Legitimate PIN returns identical `{"valid": True}`.
- **Note:** this endpoint is read-only — it does NOT mutate state or grant a
  token. But its `true` result is what Code Mode uses to gate the
  dangerous-tools toggle in the UI, so its truth matters.

#### Site 3 — `app/routers/auth.py:184` — `POST /founder-token` (JWT issuer — HIGHEST CONSEQUENCE)

```python
@router.post("/founder-token")
def founder_token(data: FounderPinRequest):
    """Issue a JWT for the founder user after FOUNDER_PIN verification.
    ...
    The PIN is verified against the FOUNDER_PIN env var."""
    import os
    founder_pin = os.getenv("FOUNDER_PIN", "<PIN>")                # 184 — BROKEN (highest consequence)
    if not data.pin or data.pin != founder_pin:
        raise HTTPException(status_code=401, detail="Invalid founder PIN")

    with get_db() as conn:
        row = conn.execute(
            "SELECT id, name, email, role, tier FROM access_users "
            "WHERE role = 'founder' AND is_active = 1 LIMIT 1"
        ).fetchone()
        if not row:
            raise HTTPException(status_code=404, detail="No founder user found")

    user = dict_row(row)
    token_data = {"user_id": user["id"], "email": user.get("email", "")}
    access  = create_access_token(token_data)
    refresh = create_refresh_token(token_data)

    return {
        "access_token": access,
        "refresh_token": refresh,
        "token_type":   "bearer",
        "user":         { "id": user["id"], ... },
    }
```

- **What PIN is compared against:** `os.getenv("FOUNDER_PIN", "<PIN>")`.
  Match → issues an **access_token** AND a **refresh_token** for the
  founder user (fetches by `role='founder' AND is_active=1`).
  Mismatch (or empty pin) → raises 401.
- **Caller gets on refusal:** **HTTP 401** with detail `"Invalid founder PIN"`.
- **What the JWT carries:** claims `{"user_id": <founder row id>, "email":
  <founder email>}` signed by `create_access_token` / `create_refresh_token`
  (defined elsewhere in `auth.py`). Whoever holds these tokens can call any
  endpoint that authorizes against the founder user — i.e. **the entire
  founder-equivalent surface** for the token lifetime.
- **Behaviour change for legitimate callers after PART 2 fix:** NONE when
  `FOUNDER_PIN` is configured (live process carries PRESENT, see Sweep §D).
  Fix closes the unset-env case: an attacker passing the literal no longer
  walks out with a founder JWT.

#### §C.1 — `app/db/init_db.py:524` (NOT a fourth broken site, but worth flagging)

```python
founder_pin = os.environ.get("FOUNDER_PIN")     # NO default — returns None if unset
if founder_pin:
    pin_hash = _hash_pin(founder_pin)
conn.execute(
    """INSERT INTO access_users (name, role, telegram_chat_id, pin_hash)
       VALUES (?, 'founder', ?, ?)""",
    ("Founder", founder_chat_id, pin_hash)

```

This is **`_migrate_access_control`** — runs at DB init / migration time, not
on every request. It seeds the founder row into `access_users`. The
`os.environ.get("FOUNDER_PIN")` has no default (returns None if unset); the
subsequent `if founder_pin:` check makes this fail-closed by accident — if
no PIN, the founder row is seeded with `pin_hash=None`, which means future
PIN-based logins via the access-controller path will fail until the operator
manually re-seeds or sets the PIN and re-runs init.

**Not** the privilege-escalation pattern the dispatch is hunting (no literal
default to fall back to). **Not** in scope for PART 2's three-site fix. Worth
noting in INFERRED for future hardening if the founder wants a CRITICAL log
here too.
